# Issue #10 / #11 受控迁移执行设计

- 日期：2026-08-02
- 状态：已获用户批准，待文档复核
- 范围：为 10 张真实试迁移提供可审计的精确选样能力；在试迁移验收和用户批准后执行全量迁移与对账
- 相关工单：#10、#11
- 相关设计：[OSS 图片资产迁移与图片级搜索设计](2026-07-31-oss-image-assets-search-design.md)

## 背景与问题

现有 `--pilot N` 按 Kodo 列表顺序选取前 N 张图片。它无法证明所选 10 张覆盖 Issue #10 要求的中文及空格路径、多层目录、JPEG/PNG/WebP、超过 20 MiB 的源图、不同路径的同内容图片和不应放大的小图。

Issue #11 是一次有条件的操作，不是 `--pilot` 的自动续步：必须在 #10 完成、验收材料附到 Ticket 后，由用户在 #10 或父 PRD 中明确批准，才能运行 `--full`。

## 备选方案

1. **精确样本清单（采用）**：迁移 CLI 接受一个 JSON 清单，按清单中的 Kodo Key 和顺序选择图片。只读校验阶段记录每项的格式、字节数、尺寸、SHA-256 与覆盖结论；写入阶段重用同一清单。清单和报告共同形成可复现的试迁移证据。
2. 继续使用 `--pilot 10` 的列表前十项。实现最少，但无法保证或证明覆盖，不能满足 #10 的验收标准。
3. 由操作者临时拼接多个 `--prefix` 运行。它不能把分散目录组合成一次恰好 10 张的迁移，也没有稳定的样本身份与对账证据。

## 设计

### 精确选样

新增可用于 `--dry-run`、`--verify-selection` 和 `--pilot` 的 `--selection-manifest PATH` 参数。清单为 UTF-8 JSON，包含有序、唯一的 `source_relative_path` 数组；清单路径绝不写入数据库。它与 `--retry-failed` 互斥，且 `--full` 拒绝该参数，防止把局部清单误当全量迁移。`--pilot` 只允许恰好 10 张，并且必须同时给出成功的 `--verified-selection-report`。

CLI 仍会先完整列举当前前缀下的 Kodo 对象，再按清单顺序匹配 Key。不存在、非图片或重复 Key 都会在写入前作为明确配置/选择错误退出；因此选样不会静默缩减。`--pilot N` 与清单项目数必须相等，防止报告中的“10”掩盖漏项。原有 `--prefix` 仍约束来源扫描范围，所有清单项必须落在该范围内。

### 只读样本验证

新增显式的只读 `--verify-selection` 模式，只能结合 `--selection-manifest` 使用。它下载清单内的源图到临时目录，计算 SHA-256、验证真实格式与尺寸，并删除全部临时文件；它不构造 OSS、embedding 或数据库写端。

报告逐项记录来源路径、源字节数、探测格式、尺寸、内容哈希和识别出的覆盖标签。报告还汇总：路径字符/层级、实际 JPEG/PNG/WebP、超过 20 MiB、小图未放大候选，以及内容哈希重复组。若清单未覆盖任一 #10 必需类别，模式以非零状态退出并在报告中明确缺项；来源实际没有该类别时，操作者可把完整扫描证据和替代方案附到 Ticket，但不能伪造“已覆盖”。

常规 `--preflight` 和完整 `--dry-run` 仍在试迁移前各运行一次：前者验证 Kodo 的只读可读性，后者固定本次实时对象、图片、非图片和字节数基线。两者均不写入外部系统。

### 试迁移与验收

`--pilot 10 --selection-manifest --verified-selection-report` 会先在只读路径重新下载十张源图，核对当前来源绑定、路径顺序、覆盖结论和每张 SHA-256 都等于成功验证报告；任何不一致均在构造 OSS、embedding 和数据库写端前停止。通过后，入库服务只从本次验证临时快照读取，不会再次读取 Kodo，避免验证到写入间的内容变化。只有该检查以及 OSS 私有 ACL、目标 Bucket/地域/隔离前缀和数据库可达性检查通过后，才调用统一入库服务。完整 JSON 报告写入指定本地证据目录，终端只输出已脱敏汇总。迁移结束后必须：

1. 核对十项报告与 `image_assets`，确认每个来源路径都有一条资产且 `model_number` 为 `NULL`；重复哈希保留两行并复用兼容预览、向量。
2. 对 OSS 原图逐项或抽样比较 SHA-256，检查私有 Bucket 与 Object Key；检查预览方向、比例、最长边、大小和小图未放大。
3. 原样重跑同一清单，确认不会重复上传、生成 embedding 或插入资产；另行识别或构造来源冲突，确认不覆盖。
4. 用至少一张试迁移源图通过搜索页面检索，保存结果、无型号展示、路径复制和私有预览 302 的截图。
5. 把命令、脱敏报告、对账表、截图和已知失败附到 Issue #10；停止，不执行 `--full`。

### 全量迁移门槛

只有下列条件全部成立才能开始 #11：

- #9 与 #10 已完成，且 #10 证据已附到 Ticket；
- 用户在 Issue #10 或父 PRD 中留下明确的全量批准；
- 已保存数据库备份或可恢复点；
- 再次运行只读 preflight 与全量 dry-run，固定当次图片数、非图片数、总字节和时间戳。

满足门槛后才显式调用 `--full --full-authorization PATH`。授权文件必须包含 #9 与 #10 证据链接、用户批准链接、数据库备份/恢复点标识，以及当次成功 preflight/dry-run 报告的相对路径和 SHA-256；CLI 会在创建写端前重新校验哈希、生成时间（过去 24 小时内）、完整扫描统计和与当前来源的 Bucket/S3 Bucket/prefix 绑定，并把当前全量枚举的统计与基线逐项比较。它还通过 GitHub API 验证 Issue #9 与 #10 已关闭、证据评论确实属于 Issue #10，且仓库所有者已在 Issue #10 或同仓库父 PRD 中作出不含否定语义的明确全量批准。全量报告必须对账 Kodo、OSS 原图对象和活跃 `image_assets`，隔离失败/冲突并允许受绑定报告约束的定向重试。Kodo 全程只读，不根据路径推断商品资料，也不会删除来源对象。

## 测试边界

经用户确认，测试聚焦两个公共边界：

1. **迁移 CLI**：清单语义、只读样本验证、缺项拒绝、报告脱敏，以及写模式的安全限制。使用假 Kodo、OSS、embedding 和数据库 seam 进行测试。
2. **真实验收流程**：Kodo → 私有 OSS → PostgreSQL → 搜索页面的 10 张试迁移与对账。它依赖真实凭证，仅在自动化测试与预检通过后执行，并以报告和截图作为证据。

不新增对实现私有方法的测试，也不为 #11 绕过用户批准门槛。

## 错误处理与安全

- 所有选择和覆盖错误都发生在 OSS、embedding、数据库写入之前。
- 来源下载仅使用专用临时目录；成功、失败和异常路径均清理文件。
- 不在日志、报告、命令参数或数据库中保存凭证、完整签名 URL 或临时绝对路径。
- 全量模式不接受样本清单；样本模式不自动升级为全量。
- 现有同路径内容冲突与 OSS 校验冲突一律不覆盖。

## 非目标

- 运行未经用户批准的全量迁移。
- 自动补充型号、分类或其他商品资料。
- 删除 Kodo 数据或让 OSS 公开读。
- 改变已有图片资产、OSS 或 pgvector 的领域模型。
